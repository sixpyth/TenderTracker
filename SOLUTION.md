# Документация решения: Микросервис трекинга статуса тендеров (Задание 6)

## Обзор задачи

Микросервис предназначен для управления тендерами и автоматического аудита всей истории их состояний. Сервис обеспечивает строгий хронологический учет изменений статуса каждого тендера, фиксируя предыдущий статус, новый статус, обязательную причину изменения и пользователя, внесшего изменения.

---

## Архитектура и технологии

Сервис построен на базе чистого асинхронного стека Python:

- **FastAPI**: Вывод REST API, swagger-документация, внедрение зависимостей (Dependency Injection).
- **SQLModel / SQLAlchemy 2.0 (Async)**: Описание ORM-моделей базы данных и работа с PostgreSQL через `asyncpg`.
- **Alembic**: Управление версионированием и миграциями схемы БД.
- **Pydantic v2**: Строгая валидация входящих и исходящих данных (DTO).
- **Docker & Docker Compose**: Контейнеризация приложения, PostgreSQL и Redis.

## Логика и алгоритм трекинга статусов

### 1. Допустимые статусы (`TenderStatus`)
Тендер может находиться в одном из 4 состояний:
- `draft` — Черновик (начальный статус)
- `active` — Активен / Опубликован
- `won` — Выигран
- `lost` — Отменен / Проигран

### 2. Атомарное создание тендера (`POST /api/v1/tender`)
1. Клиент отправляет название (`title`), описание (`description`) и опциональный стартовый статус.
2. В единой транзакции базы данных:
   - Создается запись в таблице `Tender`.
   - Автоматически формируется первая запись в таблице `TenderStatusHistory`:
     - `old_status = None`
     - `new_status = draft` (или переданный стартовый статус)
     - `reason = "Тендер создан"`
     - `changed_by_id = current_user.id`

### 3. Смена статуса с аудитом (`PATCH /api/v1/tender/{id}/status`)
1. Клиент передает `new_status` и обязательную причину изменения `reason` (минимум 1 символ).
2. Сервис находит тендер по `id`. Если тендер не найден, возвращается `404 Not Found`.
3. В единой транзакции БД:
   - Извлекается текущий статус тендера (`old_status = tender.status`).
   - Статус тендера обновляется на `new_status`.
   - Создается объективная запись в `TenderStatusHistory` с фиксацией автора изменений (`changed_by_id`), прежнего и нового статуса, а также причины.

## Схема базы данных

### Таблица `Tender`
| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID (v7) | Уникальный идентификатор тендера |
| `title` | String (index) | Наименование тендера |
| `description` | String (nullable) | Подробное описание |
| `status` | TenderStatus | Текущий статус (`draft`, `active`, `won`, `lost`) |
| `created_by_id` | UUID (FK User.id) | Автор создания |
| `created_at` | DateTime (tz) | Дата и время создания |
| `updated_at` | DateTime (tz) | Дата и время обновления |

### Таблица `TenderStatusHistory`
| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID (v7) | Уникальный идентификатор записи истории |
| `tender_id` | UUID (FK Tender.id CASCADE) | Ссылка на тендер |
| `old_status` | TenderStatus (nullable) | Предыдущий статус (null для первого статуса) |
| `new_status` | TenderStatus | Новый установленный статус |
| `reason` | String | Причина / комментарий изменения |
| `changed_by_id` | UUID (FK User.id) | Идентификатор пользователя, сменившего статус |
| `created_at` | DateTime (tz) | Дата и время записи аудита |

## REST API Эндпоинты

Все маршруты тендеров доступны по префиксу `/api/v1/tender`:

| Метод | Эндпоинт | Описание | Доступ |
|---|---|---|---|
| `POST` | `/api/v1/tender` | Создать тендер | Авторизованный |
| `GET` | `/api/v1/tender` | Список тендеров (с пагинацией и фильтрацией по `status`) | Авторизованный |
| `GET` | `/api/v1/tender/{id}` | Детали тендера (включая полную историю статусов) | Авторизованный |
| `PATCH` | `/api/v1/tender/{id}/status` | Изменить статус тендера (требует `new_status` и `reason`) | Авторизованный |
| `GET` | `/api/v1/tender/{id}/history` | Хронологический лог истории изменений статуса | Авторизованный |

## Инструкция по запуску

### 1. Клонирование и настройка окружения
```bash
git clone <repository_url>
cd backend
cp .env.example .env
```

### 2. Запуск через Docker Compose
```bash
docker compose up -d --build
```

### 3. Применение миграций и запуск сидинга
```bash
docker compose exec fastapi_server alembic upgrade head
docker compose exec fastapi_server python app/initial_data.py
```
*(Или через Makefile: `make run-dev-build` и `make init-db`)*

### 4. Проверка документации Swagger UI
Откройте в браузере: `http://localhost:8000/docs`

## Интеграционное тестирование

Для проверки полной цепочки жизненного цикла тендера подготовлен тест-сюит `app/test/api/test_tender.py`:

```bash
pytest app/test/api/test_tender.py
```
*(Или в Docker: `make pytest`)*

Тесты покрывают:
1. Авторизацию суперпользователя и получение JWT-токена.
2. Создание тендера со статусом `draft` и автосозданием стартовой истории.
3. Переход в статус `active` с сохранением причины.
4. Переход в статус `won` с проверкой полного аудит-лога.
